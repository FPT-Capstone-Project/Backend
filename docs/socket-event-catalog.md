# Socket.IO Events and Payloads

Socket.IO uses the same HTTP server as the REST API. Client events are limited to resource-room subscription and leaving. Application events are server-to-client notifications; use REST to load full resource data.

## Client to server

### `room:join`

Request:

```json
{ "type": "session", "id": 12 }
```

Supported types: `room`, `session`, `issue`, `consultation`. The payload must contain exactly `type` and `id`; `id` must be a positive integer or numeric string. Room names are generated by the backend.

Successful acknowledgment:

```json
{ "ok": true, "type": "session", "id": 12 }
```

Rejected acknowledgment:

```json
{ "ok": false, "code": "ROOM_ACCESS_DENIED" }
```

Possible error codes: `INVALID_ROOM_REQUEST`, `ROOM_ACCESS_DENIED`, `ROOM_SUBSCRIPTION_FAILED`. If no callback is supplied, the server emits rejected results through `room:subscription:error`.

### `room:leave`

Request and successful acknowledgment have the same shapes as `room:join`. Leaving does not require access to the resource.

### User presence events (Admin only)

`user:presence.snapshot` is sent to an Admin after connection:

```json
{ "userIds": [1, 7, 18] }
```

`user:presence.updated` is sent to the `admin` role room when a user's first socket connects or last socket disconnects:

```json
{ "userId": 7, "online": false }
```

Multiple tabs/connections count as one online user. Presence is kept in process memory, so a reconnect updates presence and a multi-instance deployment needs shared presence coordination. These events are not sent to Customers or Experts.

## Server to client

### `notification:new`

Sent to the authenticated recipient's private `user:{userId}` room after a notification is sent through the cultivation-session notification API.

```json
{ "notification_id": 21 }
```

The event intentionally does not include title or message. Fetch the notification through REST. Notifications created directly by other backend workflows are not currently emitted through this event.

### `payment:status.updated`

Sent to the order owner's private `user:{userId}` room after the application processes a payment status update.

```json
{
  "orderId": 11,
  "orderStatus": "PROCESSING",
  "paymentStatus": "PAID"
}
```

`orderStatus` values: `PENDING`, `CONFIRMED`, `PROCESSING`, `COMPLETED`, `CANCELLED`.

`paymentStatus` values: `UNPAID`, `PENDING`, `PAID`, `FAILED`, `REFUND_PENDING`, `REFUNDED`.

Use the event to refresh the order's payment state through REST. It is not a payment confirmation; PayOS remains the payment authority.

### `cultivation:session.updated`

Sent to the authorized `session:{sessionId}` room after the related application mutation succeeds.

Required fields:

| Field | Type | Description |
| --- | --- | --- |
| `sessionId` | number | Cultivation session ID |
| `changeType` | string | Kind of persisted change |
| `occurredAt` | string | ISO 8601 timestamp |

`changeType` values:

- `TRAYS_ASSIGNED`
- `GROWTH_UPDATED`
- `TRAY_INSPECTION_RECORDED`
- `TRAY_INSPECTION_UPDATED`
- `TRAY_INSPECTION_IMAGE_ADDED`
- `SPAWN_INSPECTION_RECORDED`
- `SPAWN_INSPECTION_UPDATED`
- `SPAWN_INSPECTION_IMAGE_ADDED`
- `SPAWN_REPLACEMENT_ISSUED`
- `HARVEST_READINESS_CHANGED`
- `STAGE_CHANGED`
- `SESSION_CANCELLED`
- `HARVEST_STARTED`
- `HARVEST_YIELD_RECORDED`
- `HARVEST_COMPLETED`
- `HARVEST_HANDOVER_COMPLETED`

Optional allowlisted fields:

| Field | Type |
| --- | --- |
| `status` | string |
| `harvestStatus` | string |
| `growthStage` | string |
| `progressPercent` | number |
| `harvestReady` | boolean |
| `growthSynchronized` | boolean |
| `inspectionId` | positive integer |
| `inspectionSource` | `MANUAL` or `AUTO` |
| `assignedTrayCount` | non-negative integer |
| `matchingTrays` | non-negative integer |
| `expectedHarvestDate` | `YYYY-MM-DD` string |

Example:

```json
{
  "sessionId": 12,
  "changeType": "GROWTH_UPDATED",
  "occurredAt": "2026-11-28T05:30:00.000Z",
  "status": "CULTIVATING",
  "harvestStatus": "NOT_READY",
  "growthStage": "PINNING",
  "progressPercent": 42,
  "harvestReady": false,
  "expectedHarvestDate": "2026-12-10"
}
```

Payload fields vary by `changeType`. The event does not include notes, inspection text, customer details, or tray-specific private details.

Daily tray inspections emit `TRAY_INSPECTION_RECORDED`, `TRAY_INSPECTION_UPDATED`, or `TRAY_INSPECTION_IMAGE_ADDED`. Automatic camera inspections use `TRAY_INSPECTION_RECORDED` with `inspectionSource: "AUTO"`. Spawn inspection creation, updates, image additions, and replacement issuance use their corresponding `SPAWN_*` change types. The event is a refresh signal; fetch inspection details and images through REST.

Daily tray inspection:

```json
{
  "sessionId": 12,
  "changeType": "TRAY_INSPECTION_RECORDED",
  "occurredAt": "2026-11-28T05:30:00.000Z",
  "inspectionId": 31,
  "inspectionSource": "MANUAL"
}
```

Automatic camera inspection uses the same event with `"inspectionSource": "AUTO"`. Spawn inspection image or replacement updates identify the inspection and action, for example:

```json
{
  "sessionId": 12,
  "changeType": "SPAWN_INSPECTION_IMAGE_ADDED",
  "occurredAt": "2026-11-28T05:30:00.000Z",
  "inspectionId": 87
}
```

### IoT/MQTT events

MQTT data is broadcast only after its database write succeeds and only to `room:{roomId}` for the room currently assigned to that registered IoT master. Clients must join the room through the authorized `room:join` request. An unassigned master is persisted where applicable but is not broadcast. The backend does not send MQTT credentials or raw MQTT topics.

#### `iot:sensor.updated`

```json
{
  "masterId": "master01",
  "nodeId": 1,
  "sensorId": 2,
  "ok": true,
  "temperature": 27.5,
  "humidity": 85.2,
  "receivedAt": "2026-11-28T05:30:00.000Z",
  "retained": false
}
```

Failed readings have `ok: false` and null `temperature`/`humidity`. `receivedAt` is the backend's MQTT arrival time; `retained: true` means the broker replayed a retained message and the reading may not be current.

#### `iot:master.status.updated`

```json
{
  "masterId": "master01",
  "status": "online",
  "receivedAt": "2026-11-28T05:30:00.000Z",
  "retained": false
}
```

#### `iot:ssr.state.updated`

```json
{
  "masterId": "master01",
  "channel": 4,
  "state": "ON",
  "receivedAt": "2026-11-28T05:30:00.000Z",
  "retained": false
}
```

SSR state is reported device state, not confirmation that a physical valve/light/fan operated or acknowledgment of a specific command. Use REST to load full sensor/SSR state and history; the Socket.IO event is a best-effort update signal.

## Rooms and authorization

The server automatically assigns `user:{userId}` to every authenticated socket, `admin` to role ID `1`, and `expert` to Expert accounts. Resource rooms are joined only through `room:join`.

- Admin and Farm Operator (role IDs `1` and `2`) can join existing resources.
- Customers can join their own session, issue, or consultation; they can join a physical room only while they have an active tray there.
- Experts can join only issues and consultations assigned to them.

## Core guarantees and limits

| Requirement | Current behavior |
| --- | --- |
| Shared HTTP server | Socket.IO attaches to the Express HTTP server on the same origin/port. |
| Authentication | JWT is verified at handshake and the active account/role is loaded from PostgreSQL. |
| Room authorization | The client submits only resource type and ID; the server authorizes access and constructs the room name. |
| Connection lifecycle | Socket.IO reconnects at the client; after reconnect the client must rejoin authorized resource rooms. |
| Online users | The server tracks active socket IDs per user and reports first-connect/last-disconnect to Admins only. This is process-local. |
| Event distribution | User/private, role and authorized resource rooms are used according to the event's audience. |
| Payload safety | Application services build explicit allowlisted payloads; do not send complete database or MQTT objects. |
| Error handling | Authentication, room authorization and realtime delivery failures are logged; delivery failures do not undo committed business writes. |
| Persistence ordering | Business writes finish successfully before their realtime event is published. Failed/rejected persistence does not broadcast the update. |
| Delivery model | Events are best-effort, not a durable queue. REST remains the source of truth; clients refresh after reconnect. |

Room membership and online presence use the in-memory Socket.IO adapter/map. For multiple backend instances, configure a shared adapter and shared presence coordination; do not assume events or online state are synchronized between processes.
